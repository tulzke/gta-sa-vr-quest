# Работа с проектом GTA San Andreas VR Quest

## Сборка

- Обычный локальный деплой на Windows — **один запуск `./tools/deploy-quest.ps1`**. Не изучать заново инструменты и не собирать цепочку ручных команд для каждого деплоя.
- Скрипт инкрементально собирает текущий код и Java-загрузчик, подписывает два APK тем же ключом и обновляет их через `adb install-multiple -r -p`, сохраняя установленные игровые/языковые splits. Билд-каталог постоянный: `build/quest-deploy`; лог: `build/quest-deploy/deploy.log`.
- Для сборки без установки — `./tools/deploy-quest.ps1 -BuildOnly`. Для первой установки, изменений игровых данных/аудио/hand assets/манифестов/OpenXR/HLOD — явно выбрать `-Full` (штатный полный builder) или `BUILD_AND_INSTALL.bat`; подробности в `BUILDING.md`.
- Локальная среда: `D:\development\SAVRBuild\tools.json`. Скрипт сам читает её; не проверять вручную каждый инструмент перед обычным запуском.
- Проверенный исходный комплект игры: `D:\QLoader\downloads\GTA - San Andreas VR v4234641+2.11.311 -NIF`. Штатная валидация нужна для нового исходного комплекта/полной сборки; при обычном деплое использовать уже подготовленные APK-шаблоны, без повторной проверки игровых данных.
- Для установки на Quest нужны USB-подключение, режим разработчика и разрешённая USB-отладка. Без шлема можно разрабатывать, запускать тесты и собирать APK.

## Установка на Quest

- После изменений мода или функциональности игры сразу устанавливать сборку на подключённый Quest, если пользователь не просил иначе. При отсутствии подключения сообщить, что установка не выполнена; использовать подходящий обычный или полный деплой согласно разделу «Сборка».
- По запросу установить сборку собирать и устанавливать нужную версию, учитывая незакоммиченные изменения и работу других агентов.
- Обычный запрос «залей/установи на шлем» означает запуск `./tools/deploy-quest.ps1` и краткий отчёт по его результату. Не запускать дополнительные тесты, проверки подписи/хешей/APK/payload, повторные pull, dumpsys, логи или пробный запуск игры, если пользователь явно этого не просил или скрипт не завершился ошибкой.
- Скрипт сам останавливает игру и копирует доступные сохранения и настройки перед установкой, без сверки хешей. `-NoBackup` использовать только если пользователь попросил пропустить бэкап. Не делать второй ручной бэкап или сверку после скрипта.
- Для обновления использовать тот же ключ подписи, что у установленной сборки. Беречь ключ и не помещать его в Git.
- Если обновление требует удаления установленной игры, сначала проверить резервную копию и отдельно согласовать удаление. Объяснить, какие внутренние данные недоступны для резервного копирования через ADB.
- При ошибке разбирать конкретную ошибку и `build/quest-deploy/deploy.log`, а не начинать полный аудит окружения. Успешный exit скрипта и ответ установщика — достаточный результат обычного деплоя.
- После установки кратко сообщать результат; не утверждать, что поведение в VR проверено, если его не проверяли в шлеме.

## Git и параллельная работа

- Перед изменениями проверять ветку и состояние рабочей директории. Не перезаписывать и не включать в свои коммиты чужие изменения.
- Каждый агент коммитит под своим именем. Кодекс коммитит под именем Codex, клод под именем Claude и т.д. Например, codex@openai.com
- По завершении каждой итерации своей работы фиксировать собственные изменения отдельным коммитом; перед коммитом убедиться, что в него не попали чужие изменения, игровые оригиналы, APK, кэш или секреты.
- Основная ветка называется `main`. При указании конкретной ветки или необходимости pull следовать запросу; для pull предпочитать `--ff-only`.
- Актуальный бэклог находится в директории `BACKLOG/`: страница индекса — `BACKLOG/index.html`, открывается двойным щелчком без сервера. При любом изменении задачи сразу редактировать `BACKLOG_DATA` в начале `BACKLOG/backlog.js`: это единственный источник номеров, названий, файлов, категорий, приоритетов и статусов страницы. Менять только явно отмеченный блок данных, сохраняя логику ниже него; не создавать отдельный JSON или копию списка в HTML. После правки достаточно обновить страницу. Подробности каждой задачи — в отдельном Markdown-файле там же с её номером и названием (например, `BACKLOG/01-nazvanie-zadachi.md`). Старый `BACKLOG/BACKLOG.md` пока сохраняется и ведётся параллельно: только номера, заголовки и метки статуса. `TODO.md` служит ссылкой на индекс. Формат данных описан в `BACKLOG/README.md`.
- Когда задача берётся в работу, сразу отмечать её статус в бэклоге: выставлять `status: "in_progress"` в `BACKLOG_DATA` в `BACKLOG/backlog.js`, добавлять `[В РАБОТЕ]` в конец заголовка задачи в `BACKLOG/BACKLOG.md` и в соответствующем подробном файле задачи. Не дублировать метку, если она уже есть.
- Когда пользователь даёт конкретную задачу на реализацию, назвать чат её номером и краткой сутью (например, «53 — Ручное управление зажиганием машины»). Если номер задачи не указан и не найден в бэклоге, использовать краткую суть без номера.
- При добавлении, переименовании, перенумерации или удалении задачи синхронно обновлять `BACKLOG_DATA` в `BACKLOG/backlog.js`, `BACKLOG/BACKLOG.md` и соответствующие файлы задач в `BACKLOG/`. Категории и приоритеты хранить только в `BACKLOG_DATA`. Сохранять незавершённые пункты, контекст и необходимые проверки; при реализации править подробный файл соответствующей задачи.
- При закрытии задачи переносить подробный файл в `BACKLOG/ARCHIVE/`, сохраняя историю и оставшиеся проверки, и убирать запись из `BACKLOG_DATA` и старого индекса. После изменений бэклога запускать `node --test tools/test-backlog.cjs`. Не считать реализацию принятой в Quest только по сборке или автотестам.
- Push выполнять только по конкретному запросу. Просьба установить сборку сама по себе не означает разрешения на push.
- При одновременной работе нескольких агентов учитывать общую рабочую директорию; деплой включает её текущее содержимое. Не превращать обычную установку в дополнительное ревью всех изменений.

## План и приоритеты бэклога

- Цель: сделать большинство механик иммерсивными и обеспечить полную сюжетную проходимость. Ближайший этап — закончить компоненты машин и передать энтузиастам массовую настройку расположения интерактивных элементов по моделям (задача 09). Саму массовую калибровку не считать предварительным условием передачи.
- `critical` — ближайшие блокеры подготовки машин: неисправные базовые взаимодействия, недостающие инструменты калибровки и предварительные зависимости вроде пригодного интерьера. Подтверждённый блокер сюжетного прохождения также получает `critical`; упоминание миссии или отсутствие нового физического устройства сами по себе не доказывают блокер.
- `high` — остальные компоненты транспорта, которые нужно завершить для передачи соответствующих моделей, сама делегируемая настройка и механики/проверки сюжетной проходимости. `medium` — остальные иммерсивные механики, удобство и исправления, не блокирующие ближайшую передачу. `low` — отложенные сложные возможности, эксперименты и косметика; полноценная ручная перезарядка (40) отложена, готовая аркадная альтернатива сохраняется. `none` — только временно для новой задачи до разбора.
- Категории описывают затронутые подсистемы и могут пересекаться. `vehicle-calibration` — массовая настройка транспорта и инструменты для неё; `story` — задачи, требующие проверки сюжетных сценариев, а не список доказанных софтлоков; `missions` — игровые задания и взаимодействия, включая необязательные; `bugs` — описанные дефекты, включая старые, а не только регрессии. Статус работы не определяет приоритет.
- Приоритет не отменяет зависимости: сначала интерьер/рабочее место, затем устройства и их калибровка. В задаче 09 учитывать готовность каждой модели: неполная спецтехника не блокирует передачу готовых обычных автомобилей. Сохранять совместимость уже выполненных калибровок. Новые устройства и изменения геометрии, осей или точек хвата учитывать до передачи затронутой модели.
- Необязательные задания не считать условием прохождения основного сюжета. При этом их физические приборы в машине (рация, телефон, таксометр и другие) входят в подготовку соответствующего салона к настройке. Реальную сюжетную проходимость подтверждать прохождением сценариев в Quest, сохраняя полезные кнопочные/стиковые пути до готовности физической замены.

## Данные и проверка изменений

- Не коммитить оригинальные игровые файлы, собранные APK, кэш, временные файлы, ключи подписи и секреты; соблюдать `.gitignore`.
- Код, конфиги и инструменты применять к пользовательской копии игры. Для крупных собственных ассетов рассматривать Git LFS; его применение и публикацию готовых архивов отдельно согласовывать.
- При разработке запускать подходящие тесты и Android-сборку для изменённой функциональности. Повторять тесты только ради деплоя не нужно. Для взаимодействий и комфорта VR отдельно отмечать необходимость проверки ощущений пользователем в Quest.
