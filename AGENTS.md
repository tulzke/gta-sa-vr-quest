# Работа с проектом GTA San Andreas VR Quest

## Сборка

- Обычный локальный деплой на Windows — **один запуск `./tools/deploy-quest.ps1`**. Не изучать заново инструменты и не собирать цепочку ручных команд для каждого деплоя.
- Скрипт инкрементально собирает текущий код и Java-загрузчик, подписывает два APK тем же ключом и обновляет их через `adb install-multiple -r -p`, сохраняя установленные игровые/языковые splits. Билд-каталог постоянный: `build/quest-deploy`; лог: `build/quest-deploy/deploy.log`.
- Для сборки без установки — `./tools/deploy-quest.ps1 -BuildOnly`. Для первой установки, изменений игровых данных/аудио/hand assets/манифестов/OpenXR/HLOD — явно выбрать `-Full` (штатный полный builder) или `BUILD_AND_INSTALL.bat`; подробности в `BUILDING.md`.
- Локальная среда: `D:\development\SAVRBuild\tools.json`. Скрипт сам читает её; не проверять вручную каждый инструмент перед обычным запуском.
- Проверенный исходный комплект игры: `D:\QLoader\downloads\GTA - San Andreas VR v4234641+2.11.311 -NIF`. Штатная валидация нужна для нового исходного комплекта/полной сборки; при обычном деплое использовать уже подготовленные APK-шаблоны, без повторной проверки игровых данных.
- Для установки на Quest нужны USB-подключение, режим разработчика и разрешённая USB-отладка. Без шлема можно разрабатывать, запускать тесты и собирать APK.

## Установка на Quest

- По запросу установить сборку собирать и устанавливать нужную версию, учитывая незакоммиченные изменения и работу других агентов.
- Обычный запрос «залей/установи на шлем» означает запуск `./tools/deploy-quest.ps1` и краткий отчёт по его результату. Не запускать дополнительные тесты, проверки подписи/хешей/APK/payload, повторные pull, dumpsys, логи или пробный запуск игры, если пользователь явно этого не просил или скрипт не завершился ошибкой.
- Скрипт сам останавливает игру и копирует доступные сохранения и настройки перед установкой, без сверки хешей. `-NoBackup` использовать только если пользователь попросил пропустить бэкап. Не делать второй ручной бэкап или сверку после скрипта.
- Для обновления использовать тот же ключ подписи, что у установленной сборки. Беречь ключ и не помещать его в Git.
- Если обновление требует удаления установленной игры, сначала проверить резервную копию и отдельно согласовать удаление. Объяснить, какие внутренние данные недоступны для резервного копирования через ADB.
- При ошибке разбирать конкретную ошибку и `build/quest-deploy/deploy.log`, а не начинать полный аудит окружения. Успешный exit скрипта и ответ установщика — достаточный результат обычного деплоя.
- После установки кратко сообщать результат; не утверждать, что поведение в VR проверено, если его не проверяли в шлеме.

## Git и параллельная работа

- Перед изменениями проверять ветку и состояние рабочей директории. Не перезаписывать и не включать в свои коммиты чужие изменения.
- Основная ветка называется `main`. При указании конкретной ветки или необходимости pull следовать запросу; для pull предпочитать `--ff-only`.
- Актуальный бэклог находится в директории `BACKLOG/`: индекс задач — `BACKLOG/BACKLOG.md`, подробности каждой задачи — в отдельном Markdown-файле там же с её номером и названием (например, `BACKLOG/01-nazvanie-zadachi.md`). Индекс содержит только номера и заголовки задач. `TODO.md` служит ссылкой на индекс.
- При добавлении, переименовании, перенумерации или удалении задачи синхронно обновлять `BACKLOG/BACKLOG.md` и соответствующие файлы задач в `BACKLOG/`. Сохранять незавершённые пункты, контекст и необходимые проверки; при реализации править подробный файл соответствующей задачи.
- Коммит и push выполнять в соответствии с конкретным запросом. Просьба установить сборку сама по себе не означает разрешения на push.
- При одновременной работе нескольких агентов учитывать общую рабочую директорию; деплой включает её текущее содержимое. Не превращать обычную установку в дополнительное ревью всех изменений.

## Данные и проверка изменений

- Не коммитить оригинальные игровые файлы, собранные APK, кэш, временные файлы, ключи подписи и секреты; соблюдать `.gitignore`.
- Код, конфиги и инструменты применять к пользовательской копии игры. Для крупных собственных ассетов рассматривать Git LFS; его применение и публикацию готовых архивов отдельно согласовывать.
- При разработке запускать подходящие тесты и Android-сборку для изменённой функциональности. Повторять тесты только ради деплоя не нужно. Для взаимодействий и комфорта VR отдельно отмечать необходимость проверки ощущений пользователем в Quest.
