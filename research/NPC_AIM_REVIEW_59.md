# 59 — Дизайн-ревью реакции NPC на прицеливание

Дата: 15 ноября 2026 года. Изучены текущие исходники форка и локальная
`.cache/vehicle-entry-research/libGame.so` (Android 2.11 arm64).
Игровой код не менялся; поведение и ощущения в Quest не проверялись.

## Вывод

Предлагается добавить мост от физического направления оружия к штатному
`CEventGunAimedAt`. Игровая система событий должна сама выбирать реакцию:
страх, поднятие рук, бегство, ответный бой либо отсутствие ответа. Нельзя
назначать всем NPC одну анимацию или принудительно очищать их задачи.

Наведение не требует нажатия триггера, взгляда вдоль ствола или отдельной
кнопки прицеливания. Отвод оружия прекращает подачу угрозы. Начавшийся бой,
бегство и розыск завершаются по штатным правилам, поэтому требование
«прекращение реакции» не означает мгновенный возврат NPC в спокойное состояние.

## Что подтверждено

| Источник | Наблюдение и следствие |
| --- | --- |
| `native/src/VrFire.cpp`, `OnPadGetWeapon` и `Update` | Физическая стрельба использует самостоятельный путь `CWeapon::Fire`, подавляя штатный ввод стрельбы. Корректные попадания сами по себе не восстанавливают реакцию на наведение без выстрела |
| `native/src/VrCamera.cpp`, запись NewState и рекрутинг | VR не использует обычный lock-on. Отдельный жест рекрутинга уже записывает `player+0x8e0/+0x8e8`; занимать эти поля ещё одним независимым владельцем рискованно |
| `CTaskSimplePlayerOnFoot::ProcessPlayerWeapon`, `0x689c5c–0x689ca4` | Штатный вызов реакции зависит от режима камеры/прицеливания и выбранной цели; вызывается `CheckForTargetToPutHandsUp(player, targetPed)` |
| `CheckForTargetToPutHandsUp`, `0x689058` | Проверяет fire type активного оружия (значение 1), seeing range NPC и исключённую задачу 601. Для NPC с группой использует `CEventGroupEvent` и `CPedGroupIntelligence::AddEvent`, для одиночного — его `CEventGroup::Add(..., false)`. Исключает группу стрелка; у CJ есть реплика, кроме оружия типа 23 |
| `CPlayerPed::Compute3rdPersonMouseTarget`, `0x5bbb2c` | Ещё один штатный путь: цель из луча камеры, собственное поле `+0x988` с reference-регистрацией и сроком `+0x990`; затем проверка оружия, seeing range и отправка события NPC/группе. Условия отличаются от helper выше |
| `CEventGunAimedAt`, конструктор `0x4eb504`, D1 `0x4eb570` | Событие занимает 0x20 байт, хранит стрелка по `+0x18`, регистрирует и освобождает entity reference. Нужен обычный деструктор D1, а не удаляющий D0 |
| `CEventGunAimedAt::AffectsPed`, `0x4eb6d0` | Исключает игрока, неживых, свою группу и задачу 601, проверяет seeing range. Есть отдельное правило для пассажиров; при ped type 6 вызывает `CCrime::ReportCrime(22, ...)` |
| `CEventGroup::Add`, `0x4e2404` | Вычисляет штатный ответ, вызывает `AffectsPed`, выполняет информирование и дальнейшую обработку. Не следует отдельно вызывать `AffectsPed` перед `Add`: у проверки есть побочный эффект с преступлением |
| `CEventGunAimedAt::GetLifeTime`, `0x4f05a8` | Возвращает 0. Однократную отправку при входе в наведение нельзя считать доказанным способом поддерживать длительную угрозу |
| `CEventHandler::ComputeGunAimedAtResponse`, `0x4f8b60`; `CTaskComplexReactToGunAimedAt`, `0x69bbf8` | Ответ зависит от текущих задач и вычисленного типа реакции; присутствуют ветки боя, бегства и анимаций. Комплексная реакция содержит собственные подзадачи и таймеры |

Это подтверждает обход штатного механизма как вероятную причину проблемы.
Точная последовательность вызовов на живом кадре и отсутствие других причин
ещё не проверены. Имена числовых task ID и полей, не доказанные отдельно,
здесь не предполагаются.

Локальные результаты дизассемблирования: `build/review59-*-disasm.txt` и
`build/review59-event-callers.txt`; библиотеку и эти временные файлы не коммитить.

## Уточнение: цикл наведения и окончание реакции

Дополнительная проверка той же библиотеки:

- Ветка `ProcessPlayerWeapon` повторно вызывает проверку цели при обновлениях
  прицеливания; это не только событие фронта «начал целиться».
- Однако task ID 601 — именно `CTaskComplexReactToGunAimedAt`:
  `GetTaskType` в `0x69d120` возвращает `0x259`. Helper
  (`0x6890cc–0x6890f8`), mouse-target путь (`0x5bbd7c–0x5bbda8`) и
  `AffectsPed` (`0x4eb6f0–0x4eb71c`) исключают NPC с этой активной задачей.
  Следовательно, повторные события не являются сигналом, который обязан
  непрерывно продлевать уже запущенную комплексную реакцию.
- `CreateSubTask` (`0x69c0c8–0x69c0d4`) сам запускает таймер на 10000 мс
  для последующей подзадачи wander (ID 912). Это таймер этой стадии, а не
  ожидание 10 секунд после отвода ствола. `ControlSubTask` проверяет его
  окончание. В цепочке также есть анимационные стадии с заданной длительностью.
- `ClearWeaponTarget` (`0x5b7bf4`) очищает lock-on через
  `SetWeaponLockOnTarget(nullptr)`, режим оружейной камеры и crosshair;
  `Clear3rdPersonMouseTarget` (`0x5b7ad0`) снимает reference и обнуляет цель.
  В этих путях нет callback NPC или события «перестал целиться».

Для проверенного механизма итог таков: цикл повторно обнаруживает угрозу,
запускает подходящую реакцию и даёт ей исполниться самостоятельно. После
снятия наведения дальнейшие проверки перестают создавать угрозу; уже
запущенная реакция не обязана немедленно заканчиваться. Модель
«каждое событие продлевает страх, отсутствие события снимает его» здесь
не подтверждается и для комплексной реакции противоречит отсечению ID 601.

## Предлагаемое поведение первого варианта

1. Игрок пешком, обычное VR-управление, оружие физически удерживается
   основной рукой с валидным tracking. Поддерживающая рука не создаёт вторую
   угрозу. Два самостоятельных оружия могут угрожать двум разным NPC;
   совпавшую цель обрабатывать один раз за игровой шаг.
2. Начальный охват: пистолеты, дробовики, SMG, автоматы, винтовки и миниган
   (типы 22–34 и 38), с проверкой свойств `CWeaponInfo`. Для первого прототипа
   исключить метательное и холодное оружие, камеру, детонатор, инструменты,
   распылители и ракетницы. Последние имеют другой fire type, и расширение
   на них требует отдельного сопоставления двух штатных путей выше.
3. Угроза не зависит от патронов, готовности к выстрелу или reload cooldown:
   NPC не должен узнавать об опустевшем магазине через VR-проверку. Во время
   перезарядки направление ствола продолжает определять угрозу.
4. Цель — первый живой NPC на конечном луче оружия, с пределом дальности из
   `CWeaponInfo` и дальнейшими штатными ограничениями NPC. Начать с точного
   луча без широкого конуса и автоматического выбора ближайшего пешехода;
   необходимость допуска на дрожание оценить в Quest. Взгляд HMD и поворот
   корпуса CJ не выбирают цель.
5. Стены, объекты и транспорт перекрывают наведение. Игрока исключать из
   world query; временные глобальные параметры запроса сохранять и
   восстанавливать на всех выходах. Проверять и отрезок от якоря руки к
   источнику луча, чтобы вынесенный за стену источник не пугал NPC сквозь неё.
6. Для активной оптики использовать тот же итоговый луч, что использует
   выстрел после `scopeaim::ApplyReticleAim`. В остальных случаях —
   `vrcam::GetWeaponFireSegment`. Не создавать второй набор калибровок AIM;
   будущая задача 73 должна менять общий источник геометрии.
7. При отводе, перекрытии, убирании/броске оружия, потере tracking, смене
   tracking epoch, загрузке, смерти CJ, паузе, меню, потере фокуса или
   передаче камеры скрипту новые события немедленно прекращаются.
   Переход на другого NPC не оставляет прежнюю цель «прилипшей».
8. Первый вариант ограничить наведением пешком на пешеходов. Наведение
   из машины, на её экипаж, DEFAULT drive-by и scripted gunner требуют
   отдельной проверки. Штатный helper для экипажа существует (`0x4eb7c8`),
   но вызов по любому попаданию луча в кузов пугал бы людей через металл.

## Архитектура и риски

Предпочтительно отдельный небольшой модуль `NpcAim`, обновляемый на
GameThread после physical ownership и scope aim. Общие gates из `main.cpp`
дополнить фокусом, паузой, жизнью игрока, владением камерой и разрешением
управления/прицеливания. Блокировку только стрельбы не трактовать автоматически
как запрет угрозы: миссии могут раздельно разрешать наведение и выстрел.
Один вызов input/render pump не считать автоматически одним шагом симуляции:
проверить порядок и ограничить отправку одним разом на цель за игровой шаг.

Модуль читает оружие каждого физического слота. Готовый `GetPhysicalRay`
в `VrFire.cpp` выбирает руку через query по типу, поэтому его нельзя без
изменений использовать для двух одинаковых пистолетов. Нужен общий запрос
геометрии с явной рукой, используемый стрельбой и угрозой, либо обращение
к существующему hand-specific API с общим применением оптики.

Для одиночных NPC использовать конструктор события, `Add(..., false)` и D1;
для групп сохранить штатный путь `CEventGroupEvent`. Готовый
`CheckForTargetToPutHandsUp` полезен как эталон, но читает единственный
активный слот CJ и вызывает его реплику: прямой вызов для оружия в другой
руке даст неверную политику. Временная подмена активного слота ради реакции
не предлагается. Групповую отправку нужно переносить с проверенными ABI,
размерами объектов и владением памятью, особенно вложенного события.

Не записывать цель угрозы в `+0x8e0`, `+0x8e8` или `+0x988`; не включать
штатную кнопку прицеливания и не поворачивать камеру/тело. Рекрутинг задачи
41, автонаведение и попадания сохраняют своих владельцев. Не заменять
событие угрозы событием выстрела.

Постоянное хранение сырого `CPed*` между кадрами запрещено. Для первого
варианта достаточно локальных целей текущего шага; если понадобятся история,
допуск или диагностика переходов, использовать проверяемый pool handle либо
корректную пару RegisterReference/CleanUpOldReference. Проверять все нужные
symbols/layout до включения модуля; при несовпадении отключать только мост
угрозы с понятной диагностикой.

## Что нужно закрыть в прототипе

- **Поддержание и окончание реакции.** Начать с отправки на каждом игровом
  шаге, как в штатной ветке `ProcessPlayerWeapon`, с устранением дублей рук.
  Проверить дедупликацию событий, повторные реплики, нагрузку и таймеры
  реакции при долгом наведении. Сохранить штатное отсечение активной задачи
  601; не продлевать её таймер вручную. Lifetime события равен нулю, но это
  не означает нулевую длительность ответа NPC. Начало таймера стадии wander
  найдено в `CreateSubTask`; проверить остальные переходы и момент повторной
  реакции при продолжении наведения после завершения предыдущей.
- **Группы и миссии.** Проверить владение вложенным событием в
  `CEventGroupEvent`, приоритет scripted tasks и штатные флаги запрета
  наведения. Нельзя гарантировать совместимость одной проверкой `IsAlive`.
- **Дальность и геометрия.** Подтвердить layout полей range/flags/fire type
  для поддержанной библиотеки, порядок world query относительно симуляции
  и отсутствие рассогласования physical snapshot/VR base при recenter.
- **Дубликаты со штатным кодом.** Проследить обе штатные ветки отправки на
  реальном кадре. Исключить двойную подачу угрозы и двойной учёт преступления
  там, где ванильная ветка всё же активна; не отключать её глобально для NPC.

Это обязательные проверки реализации, а не основания обещать готовое
поведение по одному дизассемблированию. Новый пользовательский переключатель
или ползунок для первого варианта не нужен.

## Приёмка

| Сценарий | Ожидаемый результат |
| --- | --- |
| Мирный NPC, член чужой банды, полицейский, homie своей группы, миссионный NPC | Реакцию/игнорирование выбирает штатная система; полицейский может повышать розыск. Для каждого случая сравнить со штатным наведением в том же состоянии |
| Наведение без выстрела; пустой магазин; удержание 10 секунд; отвод и повтор | Угроза работает без триггера и патронов, не перезапускает анимацию каждый кадр; после отвода новые события не приходят. Оставшиеся реакции соответствуют штатным |
| NPC за стеной/машиной, ствол у стены, соседние NPC | Нет угрозы сквозь препятствие и выбора соседней цели; штатная групповая реакция допустима |
| Левая/правая рука, одинаковые и разные пистолеты, две цели, двуручный хват | Правильный источник каждого луча, два независимых адресата, без дублей одной цели и поддержки |
| Ствол в сторону при взгляде на NPC; NPC сбоку при взгляде вперёд; оптика | Реакция следует лучу оружия/выстрела, включая штатную проверку восприятия NPC |
| Отвод, бросок, холстер, потеря tracking/фокуса, пауза, загрузка, recenter | Нет зависших целей, событий из старого tracking epoch и обращений к удалённому NPC |
| Рекрутинг, стрельба, смена оружия, катсцена, scripted gunner, посадка в авто | Нет перехвата чужих target fields, нового автонаведения, поворота камеры или изменения штатных scripted tasks |

При реализации нужны host-проверки отбора/gates и сценариев двух рук,
проверка ABI/дизассемблирования штатных вызовов, Android-сборка и обычный
деплой на подключённый Quest. Окончательная проверка реакций, устойчивости
наведения и удобства выполняется пользователем в шлеме.
