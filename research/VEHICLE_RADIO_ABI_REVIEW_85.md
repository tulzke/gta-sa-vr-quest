# 85 — Наличие радио в транспорте: ABI и дизайн-ревью

Дата: 17.11.2026. Этап: исследование и предложение дизайна.
Игровой код в этой итерации не изменён, проверка в Quest не проводилась.

## Вывод и предлагаемое решение

Для физической музыкальной крутилки использовать тип радио **текущего экземпляра
CVehicle**, а именно байт `vehicle + 0x247 == 0`. Выключенная станция не влияет
на наличие устройства. Этот способ уже реализован в `radio::VehicleHasTunableRadio`
из `native/src/RadioLabel.h` в коммите `c29a541` задачи 99; заново добавлять
список исключений моделей или отдельную проверку станции не требуется.

Штатный экспорт `IsVehicleRadioActive()` найден, но отвечает на более широкий
вопрос: он принимает типы 0, 2 и 3, включая служебное радио. Для решения,
показывать ли крутилку выбора музыкальной станции, этот bool недостаточен.
Готового экспортированного `HasTunableRadio(CVehicle*)` среди просмотренных
радиоэкспортов не найдено. Подтверждённое чтение поля экземпляра подходит лучше.

Это предложение для задачи 85, а не утверждение о её приёмке: базовое скрытие
уже есть, но остаются проверка жизненного цикла взаимодействия и испытания в Quest.

## Подтверждённые точки ABI

| Экспорт | RVA | Размер | Что даёт |
| --- | --- | --- | --- |
| `_ZN8CVehicleC2Eh` | `0x6D8AF8` | `0x364` | Конструктор передаёт `this+0x198` конструктору аудио |
| `_ZN21CAEVehicleAudioEntity10InitialiseEP7CEntity` | `0x396768` | `0x36C` | Копирует настройки модели в аудио экземпляра |
| `_ZN21CAEVehicleAudioEntity23GetVehicleAudioSettingsEs` | `0x396AD4` | `0x30` | Возвращает структуру настроек модели размером `0x24` |
| `_ZN21CAEVehicleAudioEntity43StaticGetPlayerVehicleAudioSettingsForRadioEv` | `0x396734` | `0x10` | Возвращает указатель текущей привязки радио, может быть null |
| `_ZN21CAEVehicleAudioEntity21TurnOnRadioForVehicleEv` | `0x39876C` | `0x48` | Публикует указатель `audio+0x94`, имеет побочные эффекты |
| `_ZN20CAERadioTrackManager21CheckForStationRetuneEv` | `0x3889A8` | `0x29C` | Штатный путь переключения по кнопкам |
| `_ZN20CAERadioTrackManager20IsVehicleRadioActiveEv` | `0x388C44` | `0x40` | true для типов 0, 2, 3 текущей глобальной привязки |
| `_ZN20CAERadioTrackManager10StartRadioEP21tVehicleAudioSettings` | `0x38B084` | `0x144` | Различает музыкальный и служебный запуск |
| `_ZN20CAERadioTrackManager24GetCurrentRadioStationIDEv` | `0x38B738` | `0x14` | Возвращает станцию; внутренний `0xFF` превращает в OFF=13 |
| `_ZN21CAEVehicleAudioEntity31s_pVehicleAudioSettingsForRadioE` | `0x8DF748` | `0x8` | Глобальный указатель на настройки привязанной машины |

Цепочка смещений:

```text
CVehicle + 0x198 = CAEVehicleAudioEntity
audio    + 0x094 = tVehicleAudioSettings (0x24 байта)
settings + 0x01A = выбранная станция экземпляра
settings + 0x01B = тип радио
vehicle  + 0x247 = тип радио
```

Доказательства по инструкциям:

- `0x6D8B24`: `add x0,x19,#0x198` (`0x91066260`) перед конструктором аудио.
- `0x3968CC`, `0x3968D4`, `0x3968DC`: копирование 16+16+4 байт
  в `audio+0x94`, `+0xA4`, `+0xB4`. Чтение типа из `audio+0xAF`
  по `0x3968E8` подтверждает `0x94+0x1B`.
- `0x398774`: `add x1,x0,#0x94`; `TurnOnRadioForVehicle` сохраняет этот
  указатель в глобальную привязку. По `0x398780` читает тип из `audio+0xAF`.
- `0x388AA0`: `ldrb w8,[x0,#0x1b]` (`0x39406C08`), затем
  `0x388AA4`: `cbnz w8,0x388BB4` (`0x35000888`). Типы 2 и 3 выходят
  до чтения кнопок. Тип 0 доходит до `NextStationJustUp`/`LastStationJustUp`.
  Типы 1 и значения >3 идут другой веткой; это не доступ к обычной настройке.
- `0x388C54..0x388C6C`: тот же байт выбирает результат из `0x01010001`:
  типы 0, 2, 3 активны; 1 и значения >3 неактивны. Функция не проверяет,
  разрешено ли выбирать музыкальную станцию, и не принимает `CVehicle*`.
- `0x38B738..0x38B744`: читается байт состояния менеджера `+0xE9`,
  значение `0xFF` заменяется на 13. Это состояние воспроизведения, не наличие радио.

`GetVehicleAudioSettings(short)` не стоит подключать как простой
`const Settings* (*)(short)`: дизассемблирование использует модель в `w1`
и скрытый указатель результата в `x8` (AAPCS64, возврат структуры).
К тому же функция возвращает дефолт модели, а не актуальные настройки экземпляра.
`TurnOnRadioForVehicle` нельзя вызывать для проверки: она меняет привязку и звук.

## Типы и модельные примеры

Имена типов сверены с первичным кодом реконструкции PC:
[eAERadioType](https://github.com/gta-reversed/gta-reversed/blob/master/source/game_sa/Audio/Enums/eAERadioType.h).
Числа и проверки Android подтверждены отдельно по ELF выше; PC offsets
и размеры объектов не используются.

| Байт типа | Имя в реконструкции | Музыкальная крутилка | IsVehicleRadioActive |
| --- | --- | --- | --- |
| 0 | CIVILIAN | Показывать | true |
| 1 | SPECIAL | Скрывать | false |
| 2 | UNKNOWN | Скрывать | true |
| 3 | EMERGENCY | Скрывать | true |
| 255 (`-1`) | DISABLED | Скрывать | false |
| Остальные | Неизвестное значение | Скрывать | false |

Дефолты моделей получены непосредственно из таблицы Android
`0x2617D8 + (modelId-400)*0x24`, поле `+0x1B`:

| Модели | Тип | Ожидание для крутилки |
| --- | --- | --- |
| 400 Landstalker, 411 Infernus, 560 Sultan | 0 | Есть |
| 448 Pizzaboy, 462 Faggio, 471 Quad | 0 | Есть |
| 525 Towtruck, 539 Vortex, 592 Andromada | 0 | Есть, если поддержан текущий VR-контекст салона |
| 407 Firetruck, 416 Ambulance, 523 HPV1000, 597 Police SF | 3 | Нет музыкальной крутилки; служебная рация — отдельное устройство |
| 481 BMX, 509 Bike, 510 Mountain Bike, 530 Forklift | 1 | Нет |

Среди 212 дефолтов моделей 400..611: 167 типа 0, 13 типа 1,
15 типа 3, 17 типа 255; тип 2 не встретился. Это характеристика таблицы,
не обещание появления крутилки во всех 167 моделях: остаются условия водителя,
камеры и поддержанного VR-салона. Таблица полезна для выбора проверок,
но runtime должен читать экземпляр, а не вводить whitelist/blacklist.

## Покрытие текущего кода

В `c29a541` основной объём задачи уже попал вместе с задачей 99:

- `UpdateRadioKnob` до расчёта позы/захвата проверяет `VehicleHasTunableRadio`,
  водителя и исключение велосипеда. При отказе скрывает крутилку,
  сбрасывает владельца и очередь физических переключений.
- `RADIO OFF` сохраняет видимость крутилки. Недоступное чтение станции убирает
  только текст. Перед чтением глобальной станции проверяется равенство
  привязки `StaticGetPlayerVehicleAudioSettingsForRadio()` и настроек экземпляра.
- Выбор цели в `UpdateCockpitControls`, модель в `DrawRadioKnob`,
  табличка в `DrawRadioLabel` и доступность редактирования в `VehicleDoors.cpp`
  используют `radioVisible`. Сохранённая `radioPose` эту проверку не обходит.
- `RefreshRadioTracking` повторно проверяет транспорт и тип после обновления
  камеры. `GetWheelVisualState` скрывает геометрию прежнего транспорта.
- Существующий тест `tools/test-radio-label.py --runtime-only --retail`
  покрывает OFF, типы, смену привязки, скрытие, очередь и сохранённую позу.
  Его `--retail` проверяет ABI патча таймингов задачи 99; доказательство
  смещений наличия радио приведено отдельно в этой записке.

## Что предлагается довести в реализации

1. Оставить один предикат музыкального радио по экземпляру. При небольшой
   структурной правке вынести доступ к ABI из файла глифов в общий заголовок
   радио и назвать смещения. Не дублировать вычисление `0x247` по подсистемам.
2. Перед использованием этого ABI предусмотреть однократную проверку
   характерных инструкций конструктора/инициализации и радио. При несовпадении
   скрывать физическую крутилку с одной диагностикой; кнопочный путь сохранять.
   Сейчас `g_radioRetuneLayoutReady` защищает тайминги и прогноз станции,
   но не чтение `vehicle+0x247`.
3. Централизовать отмену взаимодействия: видимость, станция, оба `radioGrabbed`,
   угол/ID, владелец, часы поворота, очередь next/prev; требовать отпускания
   grip перед новым захватом. Нельзя удалять сохранённую калибровку модели.
4. Применить отмену и при поздней потере транспорта/доступности.
   Сейчас `RefreshRadioTracking` и `GetWheelVisualState` в этих ветках меняют
   только видимость (последний ещё станцию), оставляя снимок `radioGrabbed`.
   Рендер рук в `Xr.cpp` читает `radioGrabbed` независимо от `radioVisible`,
   поэтому возможна привязка кисти к уже скрытому устройству до следующего
   обновления ввода. Это риск по чтению кода, не воспроизведённый дефект в Quest.
5. При потреблении **физической** очереди проверять актуальную машину,
   совпадение с `g_radioKnobVehicle` и тип радио. Сейчас `OnNextStationJustUp` /
   `OnLastStationJustUp` проверяют только игровой контекст и наличие машины;
   очередь может пережить позднюю пересадку до очередного `UpdateRadioKnob`.
   Альтернативные кнопки X/grip+X оставить штатному пути.
6. Vehicle Debug должен подчиняться тому же предикату: на машине без
   музыкального радио нет цели редактирования или невидимого захвата.
   Сохранённую позу оставить для последующего возвращения к подходящей модели.

Это ограниченная доводка существующей реализации; отдельные assets, настройки
для каждой модели и новые переключатели пользователю не требуются.

## Проверки перед закрытием

- Автотест отмены удержания и очереди при смене типа/машины между вводом,
  поздним обновлением камеры, выдачей состояния и потреблением события.
  Обе руки, возврат с зажатым grip, отсутствие скачка станции в новой машине.
- Quest: обычная машина с музыкой и с RADIO OFF; Firetruck/полицейская машина;
  Forklift; велосипед; обычный мотоцикл и HPV1000. Тип 2 — синтетический тест,
  пока реальная модель или сценарий с таким типом не найден.
- Пересадка в обе стороны, выход во время хвата, пассажирское место,
  пауза/катсцена и возвращение в салон. Невидимая крутилка не удерживает кисть,
  не конкурирует с другими устройствами, не выдаёт текст или щелчок.
- Старая сохранённая `radioPose` и Vehicle Debug: недоступное радио не появляется,
  после возвращения на машину с радио её поза остаётся прежней.
- После изменений игрового кода — подходящие тесты, Android-сборка и обычный
  деплой на подключённый Quest. Для текущего документального ревью сборка
  и установка не требуются. Задачу до проверки в Quest не закрывать.
